### 1.2 Ocho entidades JPA + 9 repositorios + `Templates2FlagRepository` + `BusinessSnapshotReader` + `UlidGenerator`
`src/main/kotlin/mx/evolutiondev/invitaciones/modules/templates2/persistence/`:

- `TplTemplateEntity.kt`, `TplTemplateVersionEntity.kt`, `TplAssetEntity.kt`, `TplDocumentEntity.kt`, `TplDocumentSnapshotEntity.kt`, `TplReleaseEntity.kt`, `TplTemplateRegistrationEntity.kt`, `TplAssetGcEntity.kt` — 1:1 con las 8 tablas. `@JdbcTypeCode(SqlTypes.JSON)` sobre `JsonNode` con `columnDefinition = "jsonb"`, exactamente como `02 §8.2`. `PhysicalNamingStrategyStandardImpl` (`application.yml:34`) está activo, así que **toda** columna lleva `@Column(name = "...")` explícito.
- `TplTemplateRepository.kt`, `TplTemplateVersionRepository.kt`, `TplAssetRepository.kt`, `TplDocumentRepository.kt`, `TplDocumentSnapshotRepository.kt`, `TplReleaseRepository.kt`, `TplTemplateRegistrationRepository.kt`, `TplAssetGcRepository.kt` — consultas de `02 §7.4`, nativas donde el diseño lo exige (`insertIfAbsent`/`insertIgnoreConflict` con `ON CONFLICT`, `applyRevision` que devuelve filas afectadas, `searchCatalog` con `@>` sobre `jsonb`).
- `TplDocumentRepository.lockByInvitationId` / `TplTemplateRepository.lockBySlug` — `@Lock(PESSIMISTIC_WRITE)` en JPQL (Hibernate traduce a `FOR UPDATE`), no nativas: el `FOR UPDATE` no necesita SQL crudo.
- `Templates2FlagRepository.kt` — único acceso a `invitation.uses_templates2`, con una entidad local mínima `InvitationFlagRow` (solo `id`+`uses_templates2`) como parámetro de tipo obligatorio de Spring Data, extendiendo `Repository<>` (no `JpaRepository`) para que **no** existan `save()`/`findById()` genéricos sobre una tabla que esta entidad no mapea entera. Ver ADR-2-1-05.
- `BusinessSnapshotReader.kt` — `@PersistenceContext EntityManager` + consulta nativa de proyección (`invitation` ⋈ `invitation_template` ⋈ `event_type` ⋈ `invitation_plan`); no toca `InvitationEntity`. Mapeo `eventKind`/`planTier` documentado como supuesto conservador (ADR-2-1-04, pregunta abierta).
- `UlidGenerator.kt` — ULID Crockford base32 monótono (`@Component`, `SecureRandom` por defecto, reloj inyectable para pruebas).

### 1.3 Hallazgos que obligaron a ajustar el diseño sobre la marcha
1. **`V1__initial_schema.sql` exige el rol `evolution`** (`ALTER TABLE … OWNER TO evolution` en cada tabla, dump real de producción). Ningún documento de fase 1 lo menciona; un clúster `initdb -U postgres` recién creado no lo tiene y Flyway falla `V1` con `role "evolution" does not exist". Resuelto en `PgTestCluster` (ADR-2-1-01), no en el script compartido `pg-ephemeral.sh`.
2. **`tpl_asset.sha256 CHAR(64)` necesita `@JdbcTypeCode(SqlTypes.CHAR)`**, no solo `columnDefinition`: sin esa anotación, `ddl-auto: validate` rechaza la columna real con `found bpchar, but expecting char(64) (Types#VARCHAR)` — `columnDefinition` solo afecta al DDL que Hibernate generaría, no al tipo JDBC que usa para comparar. ADR-2-1-03.
3. **`InvitationGuestEntity` (módulo antiguo) tiene un desajuste de esquema preexistente**: mapea `graduates_name`, columna que ninguna migración crea. Esto hace que **cualquier** `@DataJpaTest`/`@SpringBootTest` sin acotar entidades falle hoy, sin relación con `templates2`. Se acotó el slice de Spring de las pruebas de este bloque a `templates2.persistence` (ADR-2-1-02) en vez de tocar el módulo antiguo (prohibido). Elevado a `preguntas-abiertas.md`.

## 2. Cómo se corrieron las pruebas (Postgres sin Docker)

`scripts/pg-ephemeral.sh` (ya existente, no se tocó) es invocado **desde Kotlin** por `PgTestCluster` (`src/test/kotlin/…/persistence/PgTestCluster.kt`), no a mano: si `TPL_TEST_JDBC_URL` no está en el entorno, arranca el clúster con `TPL_TEST_STATE_DIR=/tmp/templates2-pg-2-1` (propio de este bloque), crea el rol `evolution` si falta, aplica `V1`-`V37` con `Flyway.configure()...migrate()`, y registra un shutdown hook que para el clúster al terminar la JVM de pruebas. Un solo arranque por corrida de Gradle (objeto Kotlin con inicialización perezosa). Ver ADR-2-1-01.

Esto significa que **`./gradlew test` funciona tal cual, sin ningún paso manual previo**, en este entorno sin Docker.

## 4. `ddl-auto: validate` — la prueba más importante

`DdlValidateTest` construye un `ApplicationContext` real (`@DataJpaTest` + `@AutoConfigureTestDatabase(Replace.NONE)`, acotado a `templates2.persistence` por `SpringPersistenceTestSupport`, ADR-2-1-02) contra el clúster de `PgTestCluster` con `V1`-`V37` ya aplicadas. Salida literal de un intento **fallido** durante el desarrollo (antes de la corrección de `sha256`, para que quede constancia de que la prueba de verdad detecta desajustes, no es un placebo):

```
Caused by: org.hibernate.tool.schema.spi.SchemaManagementException: Schema-validation:
wrong column type encountered in column [sha256] in table [tpl_asset];
found [bpchar (Types#CHAR)], but expecting [varchar(64) (Types#VARCHAR)]
```

Y el intento **anterior a ese**, con el `@EntityScan` sin acotar, que reveló el hallazgo #3 de la sección 1.3:

```
Caused by: org.hibernate.tool.schema.spi.SchemaManagementException: Schema-validation:
missing column [graduates_name] in table [invitation_guest]
```

Tras las dos correcciones (ADR-2-1-02, ADR-2-1-03), `DdlValidateTest` pasa en verde y queda como red de seguridad: cualquier cambio futuro a una de las 8 entidades que no case con `V29`-`V37` lo vuelve a tumbar, exactamente como pasaría en producción con `ddl-auto: validate`.

- **No se probó el trigger contra un `AssetGcJob` real** (no existe todavía): `AssetGcTriggerTest` prueba el trigger de base de datos en aislamiento (SQL puro), que es lo que compete a esta capa.
- **Cobertura de `TplDocumentSnapshotRepository`/`TplReleaseRepository`/`TplTemplateRegistrationRepository`/`TplAssetRepository`** es indirecta (ejercitadas por `CascadeDeleteTest`/`AssetGcTriggerTest`/`IdempotencyIndexesTest` vía SQL, no todas con una prueba de repositorio Spring Data dedicada como `TplDocumentRepositoryTest`). El bundle sigue en 87 % con margen sobre el 80 % exigido; no se consideró necesario añadir más pruebas solo por cobertura dado el tiempo disponible, pero un revisor puede pedir `TplReleaseRepositoryTest`/`TplTemplateRegistrationRepositoryTest`/`TplAssetRepositoryTest` explícitos si quiere más señal directa sobre esos tres repositorios.

## 6. Riesgos para el revisor

1. El mapeo `eventKind`/`planTier` de `BusinessSnapshotReader` es un supuesto conservador sin fuente en `02`/`03` (ADR-2-1-04) — revisar si el dueño del producto lo acepta.
2. `InvitationGuestEntity` tiene un desajuste de esquema real que bloquea cualquier `@SpringBootTest` completo del proyecto hoy — no es culpa de este bloque, pero cualquier bloque futuro que intente un contexto Spring sin acotar entidades lo va a golpear igual.
3. Los métodos nativos que escriben `jsonb` reciben el documento como `String` ya serializado (`CAST(:doc AS jsonb)`), no como `JsonNode`: los bloques 2-2/2-3 deben serializar con `Templates2Json.canonical(...)` antes de llamar (documentado en KDoc y en `handoffs/2-1.md`).
