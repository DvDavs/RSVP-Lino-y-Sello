### 2.3 Diff estructural y `MigrationPlan`

El diff estructural de `1.0.0` → `1.0.1` es **VACÍO** — calculado por el generador con el mismo
algoritmo que `migration/StructuralDiffCalculator.kt` y **confirmado por el backend**, que devuelve
el diff en el cuerpo del `201`:

```json
"structuralDiff": {"removedBlocks":[],"removedSections":[],"retypedBlocks":[],
                   "narrowedGroups":[],"removedPalettes":[],"removedFontSets":[],"removedVariants":[]}
```

Por tanto `migrations/1.0.0-to-1.0.1.json` es el plan vacío. **Su forma la fija el esquema, no el
brief**: `MigrationPlan` es `{templateSlug, from, to, ops}` (`packages/schema/src/manifest.ts:115-120`
y `domain/MigrationPlan.kt:48`), no `{from, to, operations}`.

```json
{"templateSlug": "boda-clasica", "from": "1.0.0", "to": "1.0.1", "ops": []}
```

El archivo **no es opcional**: declarar `migrationsFrom: ["1.0.0"]` obliga a que exista exactamente
un plan con ese nombre derivado, ni uno más (`TPL_MIGRATION_PLAN_ORPHAN`) ni uno menos
(`TPL_MIGRATION_PLAN_MISSING`), y su `templateSlug`/`from`/`to` deben casar con el nombre del
archivo (`TemplatePackageParser.kt:230-250`).

### 2.4 HALLAZGO: `contratos.md §3` no describe lo que hace el registro (P1)

`contratos.md §3` dice: «el registro de una plantilla nueva EXIGE que un diff estructural contra la
versión previa esté cubierto por un `MigrationPlan` **si el bump no es mayor**». El código hace
otra cosa, y ADR-028 también dice otra cosa:

```kotlin
// TemplateRegistrar.kt:196-203
val esMayor = pkg.manifest.version.major > anterior.version.major
if (!esMayor) { rechazarPorDiff(…, "el paquete rompe la compatibilidad …y el bump no es mayor", …) }
val plan = pkg.pkg.migrationPlans[anterior.version]
val sinCubrir = MigrationPlanCoverageChecker.uncovered(anterior, diff, plan)
```

Es decir: con un bump **menor o de parche**, un diff no vacío se rechaza con
`422 TPL_MANIFEST_BREAKING_CHANGE_NOT_MAJOR` **aunque el plan lo cubra entero** — el plan sólo se
mira cuando el bump SÍ es mayor. Un `MigrationPlan` no puede rescatar nunca un `1.0.0 → 1.0.1`.
Coincide con ADR-028 y con `01 §6.3` («un minor/patch solo puede **añadir**»), así que lo que está
mal es la frase de `contratos.md §3`. Queda como pregunta abierta; no lo corrijo por mi cuenta
porque `contratos.md` sólo lo toca el orquestador.

Consecuencia práctica para el resto de la fase 4: **cualquier cambio estructural de `boda-clasica`
que retire o estreche algo obliga a `2.0.0`**, no a `1.1.0`.

## 3. Trampas nuevas del entorno (medidas)

1. **`smoke.sh` sin `seed-demo.sh` = 4/19** (§1.1). La receta de su cabecera es incompleta.
2. **`dev-backend.sh stop` se lleva también el clúster efímero** (`scripts/dev-backend.sh:227`).

   `bootRun`; medido 23-35 s por invocación en esta máquina). La vía HTTP es instantánea con el
