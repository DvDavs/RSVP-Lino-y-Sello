# 4-0A → resto de la fase 4 · cómo levantar el entorno y registrar un paquete

Todo lo de aquí está ejecutado; la salida literal, en `evidencia/fase-4/0a/`.

## 1. Levantar todo (comandos copiables)

```bash
cd <tu worktree>
# Cada agente con SUS variables, o dos sesiones pelean por el mismo puerto y el mismo clúster.
export TPL_DEV_PORT=60NN                       # elige uno tuyo
export TPL_DEV_DB=invitaciones_f4_NN
export TPL_TEST_STATE_DIR=/tmp/templates2-pg-f4-NN
export TPL_DEV_PIDFILE=$PWD/build/dev/backend-NN.pid
export TPL_DEV_LOG=$PWD/build/dev/backend-NN.log
export TPL_DEV_BASE=http://127.0.0.1:$TPL_DEV_PORT   # <-- IMPRESCINDIBLE

scripts/dev-backend.sh start      # ~145 s la primera vez (compila)
scripts/seed-demo.sh              # ~30 s — NO ES OPCIONAL, ver §3
scripts/smoke.sh                  # esperado: 19/19 OK, exit 0
```
Sin `TPL_DEV_BASE`, `smoke.sh:16` y `seed-demo.sh:34` caen a `:6003` y golpean el backend de otro.

## 2. Registrar un paquete (P4: ni Kotlin ni reinicio)

Dos vías, las dos verificadas idempotentes (mismo `templateVersionId`, misma fila):

```bash
# A) HTTP, con el backend VIVO — la que debes usar en la fase 4 (instantánea)
docs/rediseno-plantillas/evidencia/fase-4/0a/registrar-http.sh frontend/templates/<slug>/<version>
#    → 201 {"result":"created"} la primera vez; 200 {"result":"noop_same_hash"} las siguientes

# B) línea de comandos, con el backend PARADO (arranca Spring entero: ~25-35 s por llamada)
scripts/dev-backend.sh register frontend/templates/<slug>/<version>
```
El ayudante `registrar-http.sh` crea/promueve la cuenta MASTER si hace falta, lee los assets del
propio `template.json` con `jq` (mandar de menos = `422 TPL_PACKAGE_ASSET_MISMATCH`) y manda
`migrations/` con el nombre de parte `migrations/<archivo>.json`.

## 3. Trampas nuevas (cada una costó una medición)

1. **`smoke.sh` NO es autosuficiente, aunque su cabecera lo parezca.** Sobre un clúster recién
   creado da **4/19**: la ruta 2 hace `:choose-template` sobre `xv-jardin@1.0.0`, que nadie ha
   registrado, y su `404` arrastra 13 rutas más. Con `seed-demo.sh` antes: **19/19**.
2. **`dev-backend.sh stop` para también el clúster efímero** → pierdes la base sembrada. Si sólo
   quieres liberar el puerto (p. ej. para `register`), mata el árbol del backend por
   `$TPL_DEV_PIDFILE` y deja el clúster; `register` lo reutiliza.
3. **`register` exige el puerto libre** (`dev-backend.sh:262-266`): no sirve para demostrar nada
   contra una instancia viva.
4. Sigue vigente: **nunca `./gradlew clean`** con la demostración viva (`contratos §12.6`).
5. `MigrationPlan` es `{templateSlug, from, to, ops}` — **no** `{from, to, operations}`
   (`packages/schema/src/manifest.ts:115-120`). Con la forma equivocada el registro rechaza el
   paquete.

## 5. Qué NO hay que hacer

- **No pises una versión publicada.** Cambiar un byte de `1.0.0` y re-registrarla da
  `409 TPL_VERSION_HASH_MISMATCH` y es lo correcto: se versiona, no se sobrescribe.
- **No escribas `sha256`, `bytes` ni un `package_hash` a mano** (P5). Los mide
  `build-packages.mjs`; para subir de versión, añade una entrada a su lista `DERIVADAS` y ejecútalo.
- **No cuentes con que un `MigrationPlan` rescate un bump menor o de parche.** El registro rechaza
  cualquier diff estructural no vacío si el bump no es mayor, **plan o no plan**
  (`TemplateRegistrar.kt:196-203`, ADR-028). Si retiras o estrechas algo en `boda-clasica`, es
  `2.0.0`. `contratos.md §3` dice otra cosa y está mal (pregunta abierta 4-0A).
- **No edites `frontend/templates/boda-clasica/1.0.0/**`**: está publicada y sembrada. Trabaja sobre
  `1.0.1`.
- **No borres ni cambies el `AssetEntry.id`** de un archivo entre versiones: es contrato público del
  paquete y `defaults.json` lo referencia (ADR-3B-I09-01).
- **No dejes procesos colgados**: `scripts/dev-backend.sh stop` al terminar.
