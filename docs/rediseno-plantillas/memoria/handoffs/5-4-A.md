# 5-4-A → frontend de pagos (5-4-B) y e2e · qué hay en el backend y cómo probarlo

Rama `claude/fase-5-pagos-hmb028`. Contrato: `handoffs/5-4-contrato-pagos.md` (§1–§4), con una
**nota de cinco apartamientos al final de ese fichero** que hay que leer: el más importante para el
frontend es el 5 (todos los DTO llevan `@JsonInclude(ALWAYS)` porque el `ObjectMapper` de la app
omite nulos; un campo nullable sin la anotación desaparece del JSON).

## Rutas, tal y como responden hoy
| método | ruta | quién | notas |
|---|---|---|---|
| GET | `/public/plans` | cualquiera | `{moneda, planes[], pagoEnLinea}`. `pagoEnLinea=false` sin `STRIPE_SECRET_KEY`. |
| GET | `/product/payments/invitations/{id}` | USER/ADMIN/MASTER, dueño | `404 PAY_INVITATION_NOT_FOUND` si es ajena **o** inexistente. |
| GET | `/product/payments/pagos` | USER/ADMIN/MASTER | solo los del token. |
| POST | `/product/payments/checkout` | USER/ADMIN/MASTER, dueño | cuerpo `{invitationId, planCodigo}`; `201`. Hoy `503 PAY_NOT_CONFIGURED` (no hay clave). |
| POST | `/public/stripe/webhook` | Stripe | cuerpo crudo + `Stripe-Signature`. Sin secreto, `503`. |

Errores: `{code, message, details?}`. Códigos: los siete del §3 más `PAY_INTERNAL(500)`.
Puerta de publicación: `GET …/release/preflight` devuelve `canPublish=false` con
`blockers[0].code = "TPL_PLAN_UNPAID"` y `POST …/release` responde **402** con ese código.

## Tablas
`product_plan` (V42, sembrada con `sencillo`/`fiesta`/`grande`), `product_payment` (V43),
`product_stripe_event` (V44, PK = `event.id`). `invitation.is_paid`/`total_amount` los escribe
**solo** el webhook (`InvitationPaymentFlagRepository`).

## Variables de entorno que hacen falta para cobrar de verdad
`STRIPE_SECRET_KEY`, `STRIPE_WEBHOOK_SECRET`, `STRIPE_MONEDA` (por defecto `MXN`) y `FRONTEND_URL`
(ya existe; se usa para `success_url`/`cancel_url`). **Sin las dos primeras el producto funciona**:
catálogo y consulta de plan responden, el checkout responde `503` y el webhook `503`.

## Probar el webhook a mano, con firma calculada (copiable)
```bash
SECRET='whsec_prueba_no_es_un_secreto_real'   # el mismo que STRIPE_WEBHOOK_SECRET del backend
PAYLOAD='{"id":"evt_manual_1","object":"event","type":"checkout.session.completed",
 "data":{"object":{"id":"cs_test_X","object":"checkout.session","payment_status":"paid",
 "amount_total":89900,"currency":"mxn","payment_intent":"pi_test_X",
 "metadata":{"invitationId":"3","paymentId":"1","planCodigo":"fiesta"}}}}'
PAYLOAD=$(printf '%s' "$PAYLOAD" | tr -d '\n')
T=$(date +%s)
SIG=$(printf '%s' "$T.$PAYLOAD" | openssl dgst -sha256 -hmac "$SECRET" | sed 's/^.* //')
curl -s -X POST http://127.0.0.1:6003/public/stripe/webhook \
  -H 'Content-Type: application/json' -H "Stripe-Signature: t=$T,v1=$SIG" --data-raw "$PAYLOAD"
# -> {"received":true}   y la segunda vez -> {"received":true,"duplicado":true}
```
En TypeScript es lo mismo con `crypto.createHmac('sha256', secret).update(`${t}.${payload}`)`.
La tolerancia es de **300 s**: un `t` viejo se rechaza con `400 PAY_WEBHOOK_SIGNATURE_INVALID`.
El `amount_total` **tiene que coincidir** con `product_payment.importe_centavos` o no marca pagada.

## Siembra
`scripts/seed/plan.sh` exporta `SEED_PLAN_EMAIL`, `SEED_PLAN_TOKEN`, `SEED_PLAN_SIN_PAGAR`,
`SEED_PLAN_PAGADA` y, nuevo, **`SEED_PLAN_CODIGO`** (el código del plan recomendado, consultado a
`/public/plans`). Las invitaciones se crean con `is_paid` explícito, así que `SEED_PLAN_SIN_PAGAR`
sirve tal cual para probar el `402` de la puerta.

## Qué quedó fuera (y de quién es)
- **Correo** de pago recibido / reembolsado: el transporte de marca es de E3; aquí no se manda ninguno.
- **Pantalla de eventos con `IMPORTE_DISTINTO`**: queda en `product_stripe_event`, nadie lo enseña.
  Candidato para `/admin` (E5). Ver preguntas abiertas.
- **Precios reales, `stripe_price_id` y política de reembolso**: preguntas abiertas al dueño.
- **Alta de invitación para rol USER** (`ADR-5-0B-01` punto 5): no es de esta sesión.
